HTTP over gRPC · v1alpha1

Every web app is one hop away from being a first-class gRPC upstream.

grpcgi carries HTTP exchanges over gRPC to an unmodified web application. The application process becomes an ordinary gRPC server, and gets what the gRPC ecosystem gives servers: identity and mTLS terminated in the process, xDS-managed configuration, health, deadlines, telemetry, and proxyless callers. Django, Rails, Express, Spring, a WASI component: anything with an in-process serving interface.

Why

Link gRPC and a service gets all of this. Your web app gets none of it.

A gRPC service is a first-class citizen of the mesh the moment it starts. A web app behind an HTTP proxy is a hostname with a port. grpcgi closes that gap without touching the app.

Identity in the process
The workload's certificate and mTLS terminate inside the process that runs your code, delivered over xDS. No plaintext hop on localhost, no sidecar holding the key.
xDS configuration
Listeners, routes, RBAC, and load-balancing policy arrive from the control plane like any proxyless gRPC server. Canary by config, not by redeploy.
Health and drain
grpc.health.v1 on the same port. Drain marks NOT_SERVING, sends GOAWAY, and lets in-flight exchanges finish. Zero errors per deploy.
Deadlines
The deadline the edge set reaches your request handler as a context timeout, and propagates to every call the handler makes.
Telemetry
The same per-RPC metrics, tracing, and channelz your gRPC services already export. One dashboard for the fleet.
One HTTP parser
HTTP/1.1 is parsed once, at the edge, by one fuzz-tested implementation. What reaches the app is a typed message that cannot express a malformed header.
How it works

The app process is a gRPC server

Browsers arrive at whatever HTTP gateway you already run. The gateway carries each HTTP exchange as one bidirectional gRPC stream to the application, where a thin bridge drives the framework's native interface. gRPC services in the mesh call the same process directly. Real gRPC is never wrapped.

One RPC. Everything streams.

The protocol is a single bidirectional streaming RPC, HttpBridge.Exchange. The edge sends a request head, body chunks, and optionally trailers. The application sends informational heads, one final head, body chunks, and optionally trailers. That is the same ladder as HTTP/2 itself. A server-sent-events response is a head followed by chunks for as long as the connection lives, and each application write goes on the wire immediately.

Two channels for errors

The response head is the application's status; the RPC status is the server's. A 503 from your app ends the RPC with OK. UNAVAILABLE from a draining server becomes a 503 at the edge with a retry hint every gRPC client already understands. A panic after the head has been sent becomes INTERNAL, which the edge turns into a stream reset, because lying about a committed status would be worse.

Protocol

HPACK's static table, as field numbers

Wrap HTTP headers in a protobuf and you would normally lose HPACK. So well-known header names are dedicated fields, chosen from a frozen table seeded from QPACK's static table: 90 request names, 66 response names. The receiver dispatches on an integer instead of comparing strings, and the name costs one byte. Method, scheme, authority, path, and status are typed fields. Values are bytes, because HTTP field values are bytes. Everything else rides in an overflow list.

  • Frozen. Unassigned numbers in the table range are permanently reserved. New names use headers.
  • Validated once. Header names, CRLF, obsolete folds, and Content-Length conflicts are checked at the edge. The schema cannot express a malformed header.
  • Flow control is HTTP/2's. The bridge adds no queues. Default chunk 64 KiB, hard maximum 1 MiB.
  • Native gRPC passes through. An h2 or h3 request with an application/grpc content type is routed to the app's own services on the same connection, never wrapped.
  • Golden vectors. The spec ships byte-exact vectors. The first question for a new implementation is "do you produce these bytes".
message RequestHead {
  Method   method    = 1;
  string   path      = 2;
  string   authority = 3;
  Scheme   scheme    = 4;
  bool     end_of_stream = 5;

  repeated bytes cookie     = 6;
  repeated bytes user_agent = 7;
  repeated bytes accept     = 8;
  // … 90 names. Frozen.

  string   protocol       = 201;  // "websocket"
  repeated Header headers = 211;
  bytes    resume_session = 213;
  uint64   resume_after   = 214;
}

service HttpBridge {
  rpc Exchange(stream RequestEvent)
      returns (stream ResponseEvent);
}
WebSocket and SSE

A WebSocket is what one request turns into

WebSockets get no second protocol. RFC 8441 already says a WebSocket over HTTP/2 is an extended CONNECT, so an HTTP/1.1 upgrade is normalized at the edge into exactly that. The application answers with a normal response head: 2xx accepts, anything else rejects with a real HTTP response. After that the stream carries whole messages, already unmasked, reassembled, and UTF-8 checked. Ping and pong never cross the bridge.

Server-sent events are a response that hasn't ended yet

A 200 head with text/event-stream, then one body chunk per write, for as long as the handler keeps writing. There is no buffer anywhere on the path and no idle timer to fight. When the browser leaves, the edge cancels the RPC and the handler's context is done. Last-Event-ID is just a header.

From the handler's seat

In Go the request arrives as an ordinary GET with an Upgrade header, so routing and middleware see nothing unusual. Accept it and read and write whole messages. In ASGI, websocket.accept, websocket.receive, and websocket.send map one to one. The bridge between the protocol and the framework is a lookup table, not a state machine.

Sessions

Sessions that outlive the connection

A WebSocket or an event stream normally pins a client to one process for hours. Deploys kill it, drains wait on it, and load balancing happens per connection. grpcgi decouples the two: the client's socket terminates at the edge, and the exchange behind it can end and start again on any instance without the client noticing.

  • Opt in. The application puts a session key on the final head. No key, no change: the exchange lives exactly as long as the connection.
  • Detach. Only the application lets go. It sends Detach and ends the RPC. retry_after 0 is a drain: resume now, elsewhere. 30 s means the session is idle: come back later, and the backend can scale to zero in between. An exchange the edge cancels still means the client went away.
  • Resume. The edge re-sends the request head with resume_session and resume_after: messages delivered for a WebSocket, bytes for a body. The application replays from there, or answers 410 if it no longer knows the key. Where session state lives is the application's business, as it is today.
// Go
func chat(w http.ResponseWriter, r *http.Request) {
  key, after, resumed := grpcgi.Resume(r)
  if !resumed {
    key = newSessionKey()
    grpcgi.SetSession(w, key, 30*time.Second)
  }
  ws, _ := grpcgi.AcceptWebSocket(w, r, "chat.v1", nil)
  for msg := range room.After(key, after) {
    ws.WriteText(msg)
    if draining() { ws.Detach(0); return }
  }
}
Prior art

API gateways already turn HTTP into gRPC. grpcgi extends that to the whole app.

Transcoding maps a JSON route onto a method you described in proto, and it is the right tool for an API. For a first-class API you would rather have clients call the gRPC endpoint directly. grpcgi covers the rest of the web app: pages, forms, uploads, WebSockets, event streams. Same gateway, same mesh. A complement, not a replacement.

None of this is new. CGI in 1993 said the web server handles HTTP and the application gets a structured request. FastCGI, AJP, and uwsgi refined it. Around 2010 the industry went back to proxying HTTP/1.1 to app servers because it was simpler.

Google went the other way. Inside Google the front ends terminate HTTP and speak Stubby, the ancestor of gRPC, to every backend; the request travels as a protocol buffer. You can see the fossils in public: google/rpc/http.proto, and App Engine's runtime protocol, which is literally an HttpRequest message inside an RPC. grpcgi is that idea, rebuilt on protobuf and gRPC for everyone: the control-data split from Binary HTTP, WebSockets from RFC 8441, the header table from QPACK, status translation from google.rpc.Code, the ladder from HTTP/2.

srv := grpc.NewServer(grpc.Creds(xdsCreds))

The Go module github.com/grpcgi/go serves any http.Handler from a grpc.Server: chi, gin, gorilla/mux, or your own. It includes a message-oriented WebSocket API, sessions, and an http.RoundTripper that calls a bridge back over gRPC with no proxy, so tests run end to end in-process.

Every ecosystem has the same shape

Headers plus a body stream in, headers plus a body stream out. Each bridge is a thin adapter over the same messages, and the golden vectors keep every port honest. The spec maps the exchange model onto each interface.

Built to be implemented

The schema is grpcgi.v1alpha1: stable enough to implement against, and it will not be called v1 until two independent implementations pass the conformance suite. The frozen header table is generated from one source of truth, and the golden vectors are produced by protoc --encode so there is nothing to argue about.
